# Переработка уроков и базы знаний

Источник: исходные поурочные планы первого и второго курса из папки «Документы колледжа». Сохраняются номера и учебные цели; объём упражнений уменьшен по запросу преподавателя. Исходные DOCX не изменены.

Все пары: «Что сегодня выучим» и «Задачи». Первая пара сохраняет согласованный пилот. Остальные используют общие с базой знаний определения, правильный и неправильный подход. Поля подготовки и данных необязательны; выдуманные ситуации помечены учебными. Нет обязательной квоты багов или ложного Passed без запуска.

API: встроенный клиент с 1.5, настоящий Playwright с 2.0 при включённом сервере. Возможности полного Postman, которых нет в клиенте (pm.test, CSV, экспорт, переменные), объясняются отдельно от доступных действий.

Технические источники: https://playwright.dev/docs/writing-tests ; https://playwright.dev/docs/test-assertions ; https://learning.postman.com/docs/tests-and-scripts/write-scripts/test-scripts/ ; https://www.atlassian.com/agile/kanban

## 1 курс
1. **Что делает QA и как проверять требования** Темы: Что такое тестирование. QA и QC; 7 принципов тестирования; Ошибка, дефект, баг, сбой. Практика: Прочитай CAT-02 и посчитай напитки в меню. Запиши правило, действие, ожидание и фактическое число. Совпадение тоже результат. Объясни, где здесь тестирование; назови одно действие QA до разработки.
2. **Выбрать вид проверки для понятной ситуации** Темы: Виды тестирования; Функциональное тестирование; Уровни тестирования; Чёрный, белый и серый ящик; Smoke и sanity: в чём разница; Smoke, sanity, ретест и регресс. Практика: Пройди меню → товар → корзина: это короткий smoke. Для каждого перехода сначала назови ожидаемый результат. Выбери добавление товара: подпиши «ручная, функциональная, системная, чёрный ящик» и объясни каждый признак одним предложением. Учебная ситуация: изменили расчёт количества. Назови узкую sanity-проверку, ретест одного исправления и соседнюю проверку регресса.
3. **Понять, кому задавать вопрос о продукте** Темы: SDLC и STLC: жизненные циклы разработки и тестирования; Кто делает продукт; Agile, Scrum и Kanban. Практика: Выберите роли заказчика, дизайнера, разработчика и QA. Согласуйте одно правило для учебной карточки напитка. Запиши, что QA уточнит до разработки и что проверит после. Разложи действия по SDLC и STLC простыми словами. Нарисуй To do → In progress → Review → Done, отдельно Backlog. Проведи одну задачу по колонкам и объясни, когда её можно закрыть.
4. **Исследовать один короткий путь покупателя** Темы: Карта функций и риски; Как приоритизировать тестирование при нехватке времени. Практика: Назови три функции: найти напиток, добавить в корзину, оформить заказ. Для каждой запиши, кому помешает её поломка. Выбери самую рискованную и объясни, почему проверишь её первой. Выполни по одной проверке двух функций. Подпиши вид проверки и сравни результат с правилом.
5. **Написать проверку, которую повторит сосед** Темы: Тест-кейс; Статусы проверки. Практика: Открой шаблон тест-кейса по ссылке ниже. Напиши TC-CRT-001 для удаления последнего товара: шаги и ожидание должны быть конкретными. Укажи подготовку корзины, если нужна. Удали ненужное поле данных; логин и пароль для этой проверки не требуются. Выполни кейс. После запуска запиши факт и статус; дай соседу повторить без подсказок.
6. **Отличить корректные данные от некорректных по правилу** Темы: Позитивные и негативные проверки, тестовые данные; Данные и предусловия. Практика: В требованиях найди обязательное поле оформления. Подготовь один допустимый вариант и один вариант с пустым полем. Для каждого заранее напиши ожидание. Если формат телефона не опубликован, не угадывай его: запиши вопрос ментору. Выполни обе проверки. В записи отдели нужное состояние от данных и объясни, почему правильный отказ — успешная негативная проверка.
7. **Записать короткий список наблюдаемых проверок** Темы: Чек-лист; Тест-кейс. Практика: Создай чек-лист из трёх отдельных пунктов: добавление, счётчик, удаление. В каждом должно быть понятно, какой результат нужен. Выполни пункты и поставь статусы только после проверки. Один сложный пункт разверни в тест-кейс с шагами. Сравни, какой формат легче повторить без подсказки.
8. **Отделить требование, вопрос и личное предпочтение** Темы: Требования и макеты; UI и UX; Состояния экрана. Практика: Прочитай правило пустой корзины. Найди точный результат и одно неясное место; сформулируй вопрос. Открой пустую и заполненную корзину. Запиши по одному наблюдению об оформлении UI и удобстве UX. Если ментор выдал макет, сравни одно состояние с ним. Если макета нет, так и запиши; не подменяй его своим вкусом.
9. **Выбрать значения рядом с границей** Темы: Классы эквивалентности и граничные значения. Практика: Сначала реши учебный пример «целый возраст 18–60»: назови три класса и значения у обеих границ. В кофейне найди опубликованные границы количества. Если их нет — запроси правило, не переноси правило возраста на сайт. По подтверждённому правилу проверь нижнюю границу и соседнее значение. Запиши два кейса с ожиданием и фактом.
10. **Собрать несколько разных проверок одного раздела** Темы: Тест-кейс; Другие техники тест-дизайна; Проверка работы соседа. Практика: Выбери одну функцию и напиши три кейса: обычное действие, отказ для запрещённых данных, значение у известной границы. Для учебного правила «скидка зависит от входа и кода» перечисли четыре сочетания да/нет. Ожидания уточни у ментора; это не готовое правило сайта. Обменяйся кейсами с соседом. Исправь один непонятный шаг, сохрани ID и объясни, какую технику использовал.
11. **Понять, кто и на основании чего меняет статус дефекта** Темы: Ошибка, дефект, баг, сбой; Жизненный цикл бага. Практика: Разбери учебную ситуацию: человек перепутал формулу, в коде неверный расчёт, на экране неверная сумма. Назови ошибку, дефект и сбой. Проведи карточку этого учебного бага по статусам New → Fixed → Retest → Closed; объясни пропущенную работу In progress. Представь, что после исправления сумма всё ещё неверна. Выбери следующий статус и запиши, какое доказательство приложишь.
12. **Описать воспроизводимое расхождение** Темы: Баг-репорт; Тестовое окружение, сборка и версия. Практика: Выбери подтверждённое расхождение или явно помеченный учебный пример из базы. Оформи один баг по шаблону BUG-CRT-001. Добавь только нужные предусловия и данные; отдельно запиши ожидание, факт и своё реальное окружение. Попроси соседа повторить шаги. Если не получилось — уточни запись; не придумывай находку ради задания.
13. **Показать доказательство и объяснить влияние проблемы** Темы: Severity и Priority; Скриншоты: показать баг так, чтобы его поняли; Console: собрать сообщение об ошибке; Network: найти запрос и прочитать ответ. Практика: Для двух учебных ситуаций — «заказ недоступен всем» и «опечатка в баннере перед акцией» — отдельно оцени Severity и Priority с причиной. Повтори одну свою проверку. Открой Console и Network, найди связанное сообщение или честно укажи, что его нет. Приложи один скриншот с контекстом, временем и версией. Объясни, что доказано, а что пока лишь гипотеза.
14. **Передать находку так, чтобы команда её не потеряла** Темы: Таск-трекер; Баг-трекер: оформить и передать находку. Практика: В выданном трекере поищи, не описана ли твоя проблема. Если доступа нет, используй ту же запись по шаблону в Discord. Создай одну карточку: реальный подтверждённый баг или явно учебный пример. Укажи заголовок, шаги, результаты и версию. Сохрани ID и ссылку. Попроси соседа провести ревью; меняй статус только по договорённости команды.
15. **Выбрать посильный объём итогового проекта** Темы: Тест-план. Критерии начала и завершения; Как приоритизировать тестирование при нехватке времени. Практика: Выбери свой раздел: меню, корзина или оформление. Назови две главные функции и риск каждой. Составь план на пять строк: область, версия, две проверки, условия старта, условие завершения. Объясни порядок проверок и одну вещь, которую сегодня не проверяешь.
16. **Связать правила раздела с проверками** Темы: Тест-кейс; Чек-лист; Проверка работы соседа. Практика: Для своего раздела подготовь два кейса и чек-лист из трёх пунктов. У каждого должна быть одна понятная цель. Проверь, что ожидания взяты из правил, а ненужные поля подготовки и данных удалены. Дай соседу один кейс и один пункт. Исправь запись, которую он понял иначе.
17. **Выполнить набор проверок без потери исходных условий** Темы: Функциональное тестирование; Статусы проверки. Практика: Возьми подготовленные проверки своего раздела. Сначала быстро проверь главный путь, потом выполни два кейса. После каждого действия сравни факт с ожиданием и поставь статус. При блокировке запиши причину. На подтверждённое расхождение оформи баг. Если всё совпало, сдай совпадения; обязательного числа багов нет.
18. **Исследовать продукт с конкретной целью** Темы: Исследовательское тестирование. Практика: Выбери одну цель исследования: например, сохранение корзины при переходах. Ограничь сессию десятью минутами. Пробуй связанные действия и коротко записывай путь, факт и вопросы. Не меняй всё одновременно. Сохрани одну находку или совпадение и придумай по наблюдениям один новый тест-кейс.
19. **Сравнить один сценарий в двух условиях экрана** Темы: Разные браузеры, адаптивность и мобильная версия; Мобильный экран: проверить ширину и удобство. Практика: Выбери один сценарий корзины. Выполни его на широком экране и в Responsive 390 в DevTools. Повтори в другом доступном браузере с той же версией сайта. Если браузера нет, укажи ограничение. Запиши окружение и сравнение: читаемость, доступность кнопок, результат действия. Одно отличие покажи скриншотом или запиши, что различий не заметил.
20. **Улучшить воспроизводимость и убрать дубли** Темы: Баг-репорт; Проверка работы соседа. Практика: Выбери свой или учебный баг-репорт. Проверь заголовок, воспроизводимость шагов, ожидание по правилу, факт и окружение. Сосед повторяет без устных подсказок и отмечает одно конкретное непонятное место. Исправь текст, сохрани ID. Приложи уточнение «было → стало» одной строкой.
21. **Понять условия настоящего ретеста** Темы: Ретест конкретного исправления; Жизненный цикл бага. Практика: Возьми конкретный баг и выясни, выдана ли сборка с его исправлением. Если нет — запиши «ретест не выполнен», затем разбери учебный пример из базы. При наличии исправления повтори прежние шаги с теми же данными и сохрани новый факт. Предложи Closed или Reopened с причиной. Другую обнаруженную проблему оформи отдельно.
22. **Выбрать соседние проверки после изменения** Темы: Smoke, sanity, ретест и регресс; Как приоритизировать тестирование при нехватке времени. Практика: Учебная ситуация: изменили расчёт количества. Выбери короткий smoke, узкий sanity и две соседние проверки регресса. Объясни, почему сумма и оформление связаны с изменением и что проверишь первым. Выполни доступные проверки на выданной версии. Без исправленной сборки не называй это подтверждением исправления.
23. **Посчитать результаты без ложных выводов** Темы: Метрики тестирования. Практика: Возьми пять учебных результатов: Passed, Passed, Passed, Failed, Blocked. Посчитай каждый статус. Назови число выполненных проверок и долю Passed среди выполненных; покажи расчёт. Теперь посчитай свои записи. Объясни, почему это не «процент качества всего сайта».
24. **Объяснить состояние раздела на основании доказательств** Темы: QA-отчёт (отчёт о тестировании). Практика: Собери короткий отчёт по своему разделу: версия, что проверил, статусы, ссылка на записи. Назови одну подтверждённую проблему или напиши, что в выполненных проверках расхождений не найдено. Укажи, что не проверил, оставшийся риск и следующий полезный шаг.
25. **Подготовить понятный показ собственной работы** Темы: Как показать и передать работу; Проверка работы соседа. Практика: Подготовь рассказ на две минуты: правило → проверка → факт → вывод. Открой одну свою запись. Сосед задаёт один вопрос и проверяет, открывается ли ссылка и понятны ли шаги. Уточни непонятное, сохрани пример и честно отметь незапущенные проверки.
26. **Самостоятельно защитить выводы по своему разделу** Темы: Как показать и передать работу; QA-отчёт (отчёт о тестировании). Практика: Покажи один кейс, один результат и отчёт. Объясни свой вклад, не читая чужой ответ. Ответь на один вопрос о правиле и один — о доказательстве. Если не знаешь, запиши, что уточнить. Исправь последнее замечание и передай итоговые ссылки, проверив доступ получателя.
## 2 курс
1. **Показать исходные навыки без гонки за терминами** Темы: Что такое тестирование. QA и QC; Тест-кейс; Чек-лист; Статусы проверки. Практика: Вспомни правило → действие → ожидание → факт. Проверь добавление и удаление товара по опубликованным требованиям. Запиши две проверки чек-листом. Одну разверни в тест-кейс с ID; подготовку добавь только при необходимости. Выполни кейс, поставь статус и объясни, чем проверка результата отличается от улучшения процесса QA.
2. **Передать одно наблюдение другому тестировщику** Темы: Баг-репорт; Severity и Priority; Жизненный цикл бага; Таск-трекер. Практика: Оформи один подтверждённый или явно учебный баг по шаблону. Проверь, нет ли дубликата в выданном трекере. Раздельно оцени Severity и Priority, объяснив влияние и срочность. Проведи карточку через учебные статусы и поясни, почему Fixed ещё не Closed. Если трекера нет, используй запись в Discord.
3. **Выбрать данные по классам и границам** Темы: Классы эквивалентности и граничные значения. Практика: Для учебного поля «целое число 1–10» выдели классы и шесть значений у границ: 0, 1, 2, 9, 10, 11. Сверь правило количества в кофейне с опубликованным описанием или уточнением ментора. Выполни три проверки подтверждённых границ; для каждой запиши ожидание и факт.
4. **Применить одну технику к реальному разделу** Темы: Тест-кейс; Другие техники тест-дизайна; Проверка работы соседа. Практика: Выбери функцию и составь три кейса: разрешённое действие, запрещённые данные, смена состояния. Для учебного сочетания двух условий да/нет перечисли четыре варианта без большой таблицы. Сосед выполняет один кейс. Исправь неясный шаг и назови использованные техники выбора проверок.
5. **Отличить запрос от ответа и увидеть связь с сайтом** Темы: API: как сайт общается с сервисом; Клиент, сервер и API; Network: найти запрос и прочитать ответ. Практика: Открой API-клиент лаборатории и отправь GET /products. Назови клиента, роль сервиса, запрос и ответ. Сравни один товар из Response с меню. Укажи код и важные поля, не весь ответ целиком. В DevTools → Network найди запрос по пути и времени. Если действие не вызвало обмена, запиши это наблюдение, не придумывай запрос.
6. **Понять методы HTTP и выполнить чтение, добавление, изменение и удаление в учебном API.** Темы: HTTP, методы, JSON и коды ответа; GET, POST, PUT, PATCH, DELETE; API в окне над сайтом: запрос и видимый результат. Практика: Выполни GET /products. Затем POST /cart/items с Body из примера базы и проверь корзину на сайте. PATCH /products/3 с {"price":1800} меняет учебную цену: сравни Response и карточку. Укажи метод, путь и Body отдельно. В ответе корзины найди items и поле id нужной строки. Вставь его вместо <itemId> в DELETE /cart/items/<itemId> и удали позицию. PUT объясни словами: этот запрос наш контракт не поддерживает.
7. **Прочитать статус и конкретные поля JSON** Темы: HTTP, методы, JSON и коды ответа; Как читать JSON. Практика: Возьми JSON {"productId":3,"quantity":1,"size":"M"}. Подпиши ключи, число и строку. Отправь допустимый запрос добавления. Затем quantity 0; сравни ожидаемые 201 и 400 с контрактом и фактом. Испорти JSON одной лишней запятой: укажи, отправился ли запрос вообще. Локальную ошибку JSON не называй HTTP-ответом.
8. **Самостоятельно заполнить поля клиента** Темы: API в окне над сайтом: запрос и видимый результат; Первый API-запрос без установки программ; Запросы и коллекция.
